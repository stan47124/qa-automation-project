Сборка **№29** на ревизии `bdc9e97ceba5755d77a6f7c30f213517fe1083ca`:

## Метаданные и структура отчёта

У всех тестов сохранены существующие `epic`, `feature`, `story`, имена функций,
пути модулей и параметры. Это сохраняет `testCaseId` и `historyId` текущих
непараметризованных сценариев. Случайные ID питомцев и имена рабочих папок не
добавляются в параметры идентичности тестов.

| Направление / feature | parentSuite | suite |
| --- | --- | --- |
| API: Swagger Petstore v3 | API | Swagger Petstore v3 |
| Web UI: Automation Exercise | Web UI | Automation Exercise |
| Mobile: Material Files | Mobile | Material Files |

Основное дерево Awesome настраивается через `groupBy: ["feature", "story"]`.
Параметр `hierarchies` не используется. Общий epic `QA.Guru graduation project`
сохранён как метаданные, без лишнего уровня дерева.

Severity задана явными декораторами, без изменения шагов, фикстур и assertions:

| Уровень | Количество | Сценарии |
| --- | --- | --- |
| critical | 12 | API: создание, получение, обновление, удаление; Web: данные товара, добавление, содержимое корзины, выбранное количество; Mobile: главный экран, создание папки, копирование, удаление |
| normal | 9 | API: поиск, изображение, два некорректных параметра; Web: главная, Products, поиск; Mobile: открытие каталога, переименование |
| minor | 1 | Contact Us: выбор TXT без отправки формы |

Severity оценивает последствия отказа проверяемой функции, а не длительность
теста или вероятность его падения. Blocker/trivial не назначены ради наполнения
всех категорий графика.

## Поддерживаемые графики

Типы и опции сверены с пакетами CLI 3.16.0 и проверяются реальной генерацией.

| Тип | Источник данных / ограничения |
| --- | --- |
| currentStatus | Статусы текущего запуска |
| testResultSeverities | Метки severity; No severity оставлен видимым для диагностики пропусков |
| successRateDistribution | Метки epic/feature/story и результаты тестов |
| coverageDiff | Метки и история для сравнения состава тестов; это не code coverage |
| durations | Время текущих результатов, без группировки по layer |
| statusDynamics | История запусков |
| statusTransitions | История сопоставимых тестов; при неизменных статусах переходов нет |
| testBaseGrowthDynamics | История состава набора; при постоянных 22 тестах рост нулевой |
| stabilityDistribution | История и группировка по feature |

Один epic и 22 отдельные story менее удобны для обзора стабильности, поэтому
оставлен один график по трём feature. Пустые графики layer/testing pyramid не
добавляются: соответствующих меток сейчас нет. При первом запуске нового хранилища истории ещё
нет; на следующих корректны и ровные зелёные графики, и нулевые переходы/рост.

В **3.16.0** `stabilityDistribution` дополнительно требует не меньше
`min(stabilizationPeriod, limit)` **предыдущих** запусков. С настройками проекта
это **пять предыдущих запусков**, то есть график начнёт рассчитываться начиная
с шестого полного отчёта. После двух запусков `No results` ожидаемо даже при
работающей истории и корректных метках. Лимит анализа 10 и период стабилизации 5
сохранены явно; порог не снижается ради скриншота. Это проверено по установленному
`@allurereport/web-commons@3.16.0`, `generateStabilityDistributionChart.js`.

`historyBaseUrl` и другие возможности поздних версий не используются.
Прямой вызов генератора с `allurerc.mjs` без `ALLURE_HISTORY_PATH` формирует
отчёт с группировкой и графиками, но **без сохранения истории**. Постоянная
история подключается только транзакционным helper.

## Хранение истории и защита записи

`ALLURE_HISTORY_DIR` должен указывать на постоянный локальный каталог Windows
вне Git-репозитория и вне `WORKSPACE`. Не использовать каталог сборки, `%TEMP%`,
сетевую шару или папку синхронизации для рабочей истории. Временный каталог
допустим только для изолированной проверки механизма.

```text
ALLURE_HISTORY_DIR/
└── SHA256(controller, полный Job, ветка)/
    ├── current.json                  # Атомарный указатель на проверенный снимок
    ├── commit.lock                   # Блокировка ОС; освобождается при гибели процесса
    ├── backups/                      # Предыдущие указатели перед каждым переключением
    ├── snapshots/<uuid>/
    │   ├── history.jsonl             # Неизменяемая история, максимум 20 запусков
    │   └── manifest.json             # SHA-256 и реестр опубликованных запусков
    └── transactions/<uuid>/
        ├── history.jsonl             # Рабочая копия, которую разрешено менять Allure
        └── transaction.json          # План операции и fingerprint результатов
```

Идентификатор controller берётся из `JENKINS_URL` или явно через `--server`;
Job — из `JOB_NAME`, ветка — из `BRANCH_NAME`/`GIT_BRANCH` либо явно. Пустые
Job/ветка отклоняются. Разные имена и ветки со слешами не сталкиваются благодаря
хешированию всего набора значений.

1. `prepare` читает указатель и проверяет SHA-256 существующего снимка. Первый
   запуск начинает с пустой истории, предыдущие отчёты ему не нужны.
2. Создаётся отдельная рабочая копия. Только её путь передаётся генератору через
   `ALLURE_HISTORY_PATH` → `historyPath` в `allurerc.mjs`.
3. Allure добавляет запись сам. Helper не создаёт результаты или записи запусков.
4. `commit` проверяет неизменность входных результатов, ровно одну новую запись,
   сохранение предыдущих записей в пределах лимита, имена и статусы тестов.
5. Снимок и manifest записываются с `flush/fsync`. Старый указатель сохраняется
   в backups. Затем новый указатель заменяет старый одной операцией
   `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` на Windows.

Allure никогда не переписывает активный снимок. Прерывание генерации оставляет
только незавершённую transaction. Ошибка записи снимка или указателя оставляет
предыдущую историю доступной. Повреждённый указатель/снимок не сбрасывается
автоматически в пустую историю: требуется явное восстановление.

`BUILD_TAG` или `--run-id` определяет запуск. Реестр хранит SHA-256 результатов:
повтор того же запуска с теми же данными не дописывает историю. При повторной
генерации берётся история **до** этого запуска, чтобы тест не сравнивался сам
с собой. Тот же ID с изменёнными данными отклоняется.

Проверка конфликтов выполняется под блокировкой ОС. Если другая публикация успела
изменить историю, операция завершается с ошибкой без потери записи; нужно заново
подготовить транзакцию и отчёт. Один файл не должен обслуживать разные ветки.

Лимит 20 относится к JSONL каждого актуального снимка. Снимки, резервные указатели
и реестр запусков автоматически не удаляются: их размер растёт. Очистка требует
отдельной политики хранения. Механизм рассчитан на локальную файловую систему;
это защита от прерывания процесса, а не гарантия при поломке диска.

Failed/broken сохраняются как есть, если генератор сформировал корректный запуск.
Сбой публикации/генератора не выдаётся за успешную запись истории. Инфраструктурный
Mobile testcase сохраняется отдельно от шести сценариев приложения; частичный
прогон может отражаться в графиках как изменение набора, что нужно учитывать.

Каталоги `allure-history/`, `.allure-history/` и стандартные имена JSONL исключены
из Git. Рекомендуемая рабочая история вообще находится за пределами workspace.
История содержит названия тестов и диагностические сообщения; её резервные копии
не следует публиковать без просмотра.

## Проверка прав и локальная генерация

Выберите постоянный каталог, доступный именно учётной записи агента. Пример
задаёт путь относительно профиля **того пользователя, который запускает команду**:

```powershell
$env:ALLURE_HISTORY_DIR = Join-Path $env:LOCALAPPDATA 'QA-Guru\allure-history'
.\.venv\Scripts\python.exe ci/allure_history.py probe --job qa-automation-project --branch origin/main
```

Probe проверяет создание, fsync, атомарное переименование и чтение собственных
временных файлов; ACL не меняет. Путь и команду нужно проверить в контексте
реального агента перед подключением. При отказе доступа не изменять ACL
автоматически. Проверка текущим пользователем не подменяет эту проверку.

Для самостоятельной генерации нужен установленный CLI ровно 3.16.0. `--cli`
указывает на JavaScript `cli.js` пакета `allure`, Node.js должен быть в PATH.
Для воспроизведения проверенного окружения передайте `--node` с исполняемым
файлом Node.js **24.14.1**, как в инструменте Jenkins. На системном Node.js 26.13.0
одна повторная генерация завершилась ошибкой, а диагностическое логирование
Allure в пользовательский `.allure` было запрещено песочницей. Рабочая история
при этом сохранилась. Три генерации на Node.js 24.14.1 прошли успешно.
Используйте реальную папку результатов и новый каталог вывода:

```powershell
$results = Read-Host 'Путь к существующему allure-results'
$allureCli = Read-Host 'Путь к allure/cli.js версии 3.16.0'
$nodeExe = Read-Host 'Путь к node.exe версии 24.14.1'
$output = 'artifacts/allure-local-' + [guid]::NewGuid().ToString('N')
$runId = Read-Host 'Уникальный постоянный ID этого реального запуска'
.\.venv\Scripts\python.exe ci/allure_history.py generate --job qa-automation-project --branch origin/main --run-id $runId --results $results --cli $allureCli --node $nodeExe --output $output
& $nodeExe $allureCli open $output
```

Для повторной генерации используйте тот же `runId` и те же результаты, но новый
`output`. Для другого реального запуска нужен другой ID. Старые файлы результатов
не редактируются, severity им задним числом не добавляется.

## Подключение к Jenkins

Совместимость `configPath` подтверждена на JAR агента, как описано выше.
При замене плагина повторите проверку против его новой версии. Для воспроизведения
Java-пробы нужен JDK 17+ и classpath из agent.jar и JAR remoting-кэша:

```powershell
$agentRoot = Read-Host 'Корень Windows-агента'
$jars = @(Get-ChildItem -LiteralPath "$agentRoot/remoting/jarCache" -Recurse -File -Filter '*.jar' | ForEach-Object FullName)
$probeClasspath = (@("$agentRoot/agent.jar") + $jars) -join ';'
java --class-path $probeClasspath ci/CheckAllurePlugin.java
```

Подготовленное подключение в `publishResults`:

1. Сохранить существующий JUnit и список `resultPaths`, Poll SCM и все стадии тестов.
2. Корень задаётся параметром `ALLURE_HISTORY_DIR`; пустое значение выбирает
   `LOCALAPPDATA/QA-Guru/allure-history` пользователя агента. Probe выполняется
   перед публикацией. Полное имя Job берётся из окружения, branch сохраняется
   из результата `checkout scm` в `QA_HISTORY_BRANCH`, включая путь через `post`.
3. Вызвать `prepare` с теми же каталогами, которые получит Allure. Сохранить
   выведенный путь JSONL и передать его как `ALLURE_HISTORY_PATH` в `withEnv`.
4. Вызвать существующий `allure` с дополнительным
   `configPath: 'allurerc.mjs'`, сохранив `commandline`, `ALWAYS` и все результаты.
5. Только после успешной генерации вызвать `commit --transaction <каталог>`.
   Не выполнять commit в `finally` после неуспешного генератора.
6. Скопировать выбранный проверенный снимок и manifest в новый подкаталог
   текущего `REPORT_ROOT` для существующего архивирования; внешнее хранилище
   не включать в широкую маску. Снимок с manifest содержит реестр запусков.
7. Сохранить защиту от двойной публикации и публикацию при падениях тестов.

Если root/probe/prepare недоступны, Pipeline публикует текущие результаты с
конфигурацией без истории и явно отмечает сборку UNSTABLE. Ошибка commit/export
также видима, готовый Allure сохраняется. Если сам генератор бросает ошибку,
commit не вызывается. JUnit публикуется до Allure; исходное архивирование в
`post` сохраняется. Публикация и семь записей истории подтверждены артефактами №29.

В архиве №29 проверены `history-snapshot/history.jsonl`, manifest и snapshot ID.
История №23–29 содержит реальные результаты; первая запись относится к №23.
После последующих штатных сборок проверяйте JUnit/Allure, severity 12/9/1,
три feature и одну новую запись для данного run ID. Публикация одного запуска
повторно не должна увеличивать историю. Job вручную запускать не требуется.

## Восстановление

Остановите конкурирующие публикации административным процессом команды; helper
сам не меняет Job. Выберите ранее проверенный ID из `snapshots/` или backups.

```powershell
$snapshotId = Read-Host 'ID проверенного снимка из snapshots'
.\.venv\Scripts\python.exe ci/allure_history.py restore --job qa-automation-project --branch origin/main --snapshot $snapshotId
```

Restore проверяет SHA-256 и формат JSONL, сохраняет старый указатель и атомарно
переключает его. Результаты тестов и старые снимки не удаляются. После отката
история отражает выбранный момент; потерянные более поздние реальные запуски
можно повторно сгенерировать из их оригинальных результатов с прежними ID.

При потере всего каталога восстановите снимки и manifest из доверенных архивов
сборок в ту же namespace: `history-snapshot/snapshot.json` содержит исходные
namespace и snapshot ID. Затем выполните restore. Одного JSONL недостаточно для
сохранения реестра дедупликации. Для регенерации старого запуска нужен и его
предыдущий снимок; если тот утрачен, операция завершится ошибкой, а не добавит
дубликат. Не исправляйте статусы в JSON вручную.

```powershell
$check = 'artifacts/allure-check-' + [guid]::NewGuid().ToString('N')
.\.venv\Scripts\python.exe -m pytest ci/tests/test_allure_history.py -q --basetemp="$check/tmp" --alluredir="$check/allure-results" --junitxml="$check/junit.xml"

```

Для проверки ID добавьте к `check_allure_metadata.py` параметр
`--baseline <путь к реальному прежнему allure-results>`.

Пробная генерация копирует два реальных набора, создаёт отдельную временную
историю вне репозитория и проверяет последовательность 1 → 2 → 2 при повторе:

```powershell
$first = Read-Host 'allure-results первого реального прогона'
$second = Read-Host 'allure-results второго реального прогона'
$allureCli = Read-Host 'Путь к allure/cli.js версии 3.16.0'
$nodeExe = Read-Host 'Путь к node.exe версии 24.14.1'
.\.venv\Scripts\python.exe ci/verify_allure_report.py --first $first --second $second --cli $allureCli --node $nodeExe
```

Скрипт предназначен для двух полных прогонов проекта по 22 теста. Он проверяет
неизменность исходных файлов, 22 элемента дерева, три feature и девять типов
графиков. Созданные отчёты, копии и временная история сохраняются для просмотра.
Новые метки проверяются collection; старые результаты остаются с прежними метками.

## Источники совместимости

Следующий абзац фиксирует историческую приёмку первоначального внедрения Allure,
а не новый запуск и не текущее количество infrastructure-тестов. Текущее
подтверждение полного CI-прогона №29 приведено в начале документа.

Локальная проверка изменений: **125 passed** в `ci/tests`, collection 22 тестов,
severity 12/9/1, совпадение всех 22 `historyId`/`testCaseId` с реальными прежними
результатами. Тела функций шести тестовых модулей не изменились. Установленный
инструмент агента (CLI 3.16.0 / Node.js 24.14.1) сформировал три отчёта на копиях
двух настоящих прогонов: 22 теста, три feature и девять типов графиков в каждом;
история 1 → 2 → 2, исходные результаты не изменены. Новый полный прогон приложений
не выполнялся; старые успешные результаты не выдаются за новый запуск.

- [AwesomeOptions, тег v3.16.0](https://github.com/allure-framework/allure3/blob/v3.16.0/packages/plugin-awesome/src/model.ts).
- [Реализация historyPath, тег v3.16.0](https://github.com/allure-framework/allure3/blob/v3.16.0/packages/core/src/history.ts).
- [Жизненный цикл генерации, тег v3.16.0](https://github.com/allure-framework/allure3/blob/v3.16.0/packages/core/src/report.ts).
- [Allure Pipeline step](https://www.jenkins.io/doc/pipeline/steps/allure-jenkins-plugin/).

Современная онлайн-документация может описывать более новые версии. Локальная
генерация CLI 3.16.0 проверяет конфигурацию; Java-проба проверяет установленный
плагин отдельно. Фиктивные снимки отчёта и искусственные бизнес-результаты не создаются.
