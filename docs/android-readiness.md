# Готовность Android в Mobile CI

`ci/mobile_ci.py` сохраняет общий бюджет подготовки Android **180 секунд**.
После существующей проверки загрузки и PackageManager вызывается общий модуль
`tests/mobile/android_readiness.py`. Все ADB-запросы ограничены оставшимся
временем; повторный опрос выполняется только пока состояние не подтверждено.

Проверяются:

- ADB state `device` и `sys.boot_completed=1`;
- регистрация ActivityManager/ActivityTaskManager, PackageManager,
  WindowManager, InputManager и AccessibilityManager;
- ответы `am get-current-user`, `pm path android`, `wm size`,
  `dumpsys input`, `dumpsys accessibility`;
- наличие Material Files, разрешение launcher и настроенной Activity
  для текущего Android-пользователя.

Регистрация Binder-сервиса сама по себе недостаточна. Ответы на read-only
запросы также не гарантируют успешность следующей instrumentation: это
наблюдаемые условия допуска, а не доказательство отсутствия будущих сбоев.
В частности, системный ANR-диалог может перекрывать приложение даже при
успешных ответах сервисов; readiness не закрывает такие диалоги автоматически.
Опрос не запускает приложение или instrumentation. Существующая подготовка
приложения после readiness остаётся отдельной операцией.

Перед каждой Appium-сессией выполняется один диагностический снимок
с общим лимитом **5 секунд**, максимум **2 секунды** на запрос.
Он не блокирует создание сессии при неподтверждённом состоянии и не повторяет
factory. Это дополнительная нагрузка, учитываемая существующим лимитом
Mobile pytest **600 секунд**. Appium timeout **60 секунд** и ADB timeout
**20 секунд**, capabilities и порядок тестов сохранены.

## Наблюдения

В каталоге текущего Mobile-прогона сохраняется `android-readiness.jsonl`:
время UTC, названия проверок, классификации результатов, длительности,
подготовка устройства и доступные сведения о загрузке эмулятора.
Для уже работающего устройства время загрузки неизвестно и остаётся `null`.
Для собственного запущенного эмулятора читается ограниченный конец его лога:
сохраняются только классификация загрузки и числовая длительность.

Allure получает JSON-вложения `Mobile: Android readiness before session`
и `Mobile: session initialization timing`. Сохраняются числовые показатели
host CPU/RAM, Android MemAvailable/load average и задержки запросов.
CPU вычисляется между естественными точками измерения; первое значение
может быть `null`. Порогов CPU/RAM для отказа нет. При исчерпании бюджета
часть диагностических показателей может быть недоступна.

Сырые `dumpsys`, списки пакетов, пользовательские пути и содержимое
переменных окружения в новые JSON не записываются. Существующие технические
логи runner/Appium сохраняют прежний формат и требуют отдельного контроля
перед публичным размещением. Конфигурация постоянной истории Allure не меняется.

## Временная метка logcat

Дата запрашивается как `date +%m-%dT%H:%M:%S.000`, без пробела в аргументе
удалённого shell. Проверяются exit code, формат и календарная корректность;
`T` заменяется пробелом только после проверки. Точность маркера — секунды.
Причины отсутствия маркера различаются: `nonzero_exit`, `invalid_format`,
`timeout`, `exception`. Без маркера сводка явно помечена
`unscoped_recent_events`. Ошибки диагностики и вложений не заменяют исходную
ошибку создания Appium-сессии.

## Проверка

Инфраструктурные тесты запускаются через `.venv` с отдельным `--basetemp`
внутри `artifacts`. Функциональное сравнение требует двух новых каталогов
результатов: cold (собственный выключенный AVD, `-no-snapshot-load
-no-snapshot-save`) и warm (тот же работающий AVD). Нельзя выполнять wipe-data,
удалять snapshot, завершать чужой эмулятор или повторять упавший тест ради
успеха. Перед запуском необходимы свободные порты и блокировка устройства.
Для Pipeline окончательная проверка — следующий согласованный автоматический
прогон через Poll SCM, с анализом JSONL и шести реальных результатов Mobile.
