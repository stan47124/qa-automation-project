# Результаты PoC: Swagger Petstore

> **Исторический материал.** Сведения ниже относятся к дате проверки и могут
> отличаться от текущего кода. Актуальный результат — Jenkins №29, 22 passed;
> инструкции и навигация: [документация проекта](README.md).

Дата проверки: 30 октября 2026 года.

## Подтверждённые операции

Диагностический тест `tests/api/test_petstore_smoke.py` успешно выполнил полный жизненный цикл собственной сущности:

1. `POST /pet` создал питомца с уникальным ID — HTTP 200.
2. `GET /pet/{petId}` вернул созданного питомца — HTTP 200; значения `id`, `name`, `photoUrls`, `status`, `category` и `tags` совпали с отправленными данными.
3. `POST /pet/{petId}/uploadImage` загрузил PNG размером 1×1 пиксель — HTTP 200.
4. Ответ загрузки содержал исходные данные питомца и дополнительный путь к файлу в `photoUrls`.
5. `DELETE /pet/{petId}` удалил созданную запись — HTTP 200.
6. `GET /pet/{petId}` после удаления вернул HTTP 404.

Очистка повторяется в блоке `finally`, поэтому выполняется и при ошибке промежуточной проверки. Результат завершающего DELETE проверяется: допустим HTTP 200, если запись ещё существовала, или HTTP 404, если она уже была удалена основным сценарием. После этого контрольный GET обязан вернуть HTTP 404.

Последний запуск завершился результатом `1 passed`. Дополнительный GET по использованному ID после завершения pytest также вернул `404 Pet not found`, что независимо подтвердило отсутствие тестовой записи.

## Расхождение `uploadImage` с OpenAPI

OpenAPI 3.0.4 для успешного ответа `POST /pet/{petId}/uploadImage` с `application/json` ссылается на `#/components/schemas/ApiResponse`. Эта схема описывает поля:

- `code`;
- `type`;
- `message`.

Фактически Petstore вернул HTTP 200 и JSON полной сущности `Pet` со следующими полями:

- `id`;
- `category`;
- `name`;
- `photoUrls`;
- `tags`;
- `status`.

В `photoUrls` был добавлен серверный путь загруженного файла вида `/tmp/inflector...tmp`. Поля `code`, `type` и `message`, заявленные схемой `ApiResponse`, в фактическом ответе отсутствовали.

Следовательно, операция загрузки работоспособна, но фактический JSON-ответ не соответствует объявленной OpenAPI-схеме успешного ответа. Текущий диагностический тест намеренно проверяет наблюдаемую структуру `Pet`; это расхождение следует учитывать при дальнейшем проектировании API-проверок.

# Результаты PoC: Automation Exercise UI

Дата проверки: 30 октября 2026 года.

## Окружение

- Python 3.14.3;
- pytest 9.2.0;
- Selene 2.0.0rc10;
- Selenium 4.52.0;
- локальный Google Chrome 156.0.8078.49.

Первоначально Selene и Selenium отсутствовали в виртуальном окружении. Стабильная версия `selene 1.0.2`, выбранная pip без prerelease-флага, оказалась несовместима с актуальным Selenium. Для PoC установлена современная версия `selene 2.0.0rc10`, поддерживающая API `browser`, `be` и `have`.

## Проверенные элементы и локаторы

Фактическая HTML-разметка страницы `https://automationexercise.com/products` содержит:

- ссылку каталога `a[href="/products"]`;
- поле поиска `#search_product`;
- кнопку поиска `#submit_search`;
- контейнер результатов `.features_items`;
- названия товаров `.features_items .productinfo p`.

В каталоге подтверждено наличие товара `Blue Top`.

## Результат диагностического теста

Тест `tests/ui/test_product_search.py` выполнил следующий сценарий:

1. Открыл главную страницу Automation Exercise.
2. Перешёл в каталог через ссылку Products.
3. Дождался URL, содержащего `/products`.
4. Ввёл существующее название `Blue Top` и запустил поиск.
5. Проверил появление заголовка `SEARCHED PRODUCTS`.
6. Проверил, что результаты присутствуют и содержат ровно один товар с названием `Blue Top`.

Все ожидания реализованы средствами Selene; `time.sleep()` не используется. Браузер закрывается в блоке `finally`.

Локальный запуск в Chrome завершился успешно:

```text
tests/ui/test_product_search.py::test_search_for_existing_product PASSED
1 passed in 17.12s
```

Диагностический PoC подтверждает техническую возможность автоматизировать поиск товаров на Automation Exercise через Selene и локальный Chrome. Проверка не является полноценным UI-фреймворком и не подтверждает стабильность остальных страниц или сценариев сайта.

## PoC загрузки файла через Contact Us

Страница `https://automationexercise.com/contact_us` доступна и содержит форму с методом `POST` и action `/contact_us`. Подтверждены реальные локаторы:

- `[name="name"]` — имя;
- `[name="email"]` — email;
- `[name="subject"]` — тема;
- `[name="message"]` — сообщение;
- `input[type="file"][name="upload_file"]` — выбор файла;
- `[name="submit"]` — отправка формы;
- `.contact-form h2` — заголовок `GET IN TOUCH`.

Тест `tests/ui/test_contact_us_upload.py` создал временный файл `contact_upload.txt` через fixture `tmp_path`, заполнил поля тестовыми данными и передал абсолютный путь файла в `input[type="file"]`. Затем Selene дождался, пока значение input будет содержать имя `contact_upload.txt`, что подтвердило выбор файла браузером.

Форма не отправлялась. Её отправка создаёт внешнее обращение, а на странице не найдено подтверждение, что введённые сообщения гарантированно отбрасываются и никому не доставляются. Для технической проверки механизма загрузки достаточно безопасной проверки file input без `POST` формы.

Все ожидания выполнены средствами Selene без `time.sleep()`. Chrome гарантированно закрывается в `finally`, а временный файл удаляется механизмом pytest после завершения теста.

Локальный результат:

```text
tests/ui/test_contact_us_upload.py::test_contact_us_file_upload PASSED
1 passed in 5.85s
```

PoC подтверждает, что локальный Chrome и Selene способны прикрепить TXT-файл к форме Contact Us. Успешная серверная обработка формы и сообщение подтверждения этим тестом намеренно не проверялись.
